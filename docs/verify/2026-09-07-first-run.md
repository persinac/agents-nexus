## 1. management-api#112 — `dd5efba` — **CONFIRMED**, and the premise needs correcting

**Reclassify: `UNFALSIFIABLE` → `CONFIRMED`.** The PR carries no `VERIFY:` line, so the
script was right to flag it, but the body contains a falsifiable claim in prose

### The predicate claim — independently confirmed, but not a defect

The orchestrator's report was that the three new predicates are wired to no query.
**That is true.** Checked at the merge commit itself, not at HEAD — local HEAD was
`0a009f9` on a feature branch, and `patron.py` picks up `_REAL_CUSTOMER_USER_COND` in

`git grep -a <name> dd5efba -- app/` → five references, all in `app/crud/purchases.py`:

| line | what it is |

| 181 | defines `_REAL_CUSTOMER_ACTIVITY_FILTERS` |
| 183, 184 | compose the first two *into* 181 |

Zero query call sites. **CONFIRMED — VERIFIED, `git grep -a … dd5efba -- app/`.**

**But the framing must not survive this report.** This was not an oversight. The PR body
states it four separate times, and `TestAdditiveScopeGuard` *enforces* it: it runs
`inspect.getsource` over the four query functions and fails if any new name appears.
That is an executable guard, not a string match, and it can fail. Describing this merge as
"wired to nothing" without that context misrepresents the author — the restraint was the
deliberate product, because the synthetic heartbeat is ~97% of play rows and wiring these
in would move operator-visible numbers by orders of magnitude.

The guard's four functions are exactly the four DB-querying entry points in the module;
the other five `def`s (`_classify_play`, `_truncate`, `build_comparison_buckets`,
`build_machine_buckets`, `daily_revenue_windows`) are pure helpers. **Guard coverage is
complete as of `dd5efba`** — VERIFIED, `git show dd5efba:app/crud/purchases.py | grep "^def "`.

### Two findings worth acting on

1. **The task definition is not evidence of what is deployed.** `flashback-fleet-management-api:7`

   The load-bearing evidence is the **ECR push timestamp** plus `/health`.
   VERIFIED — `aws ecs describe-task-definition`, `aws ecr describe-images`.
2. **The guard hardcodes four function names.** A fifth query function added later that used

> **Corrected (2026-09-07, via `storefront-api` and `ui-integration-tests`).** I originally
> argued this from timing: the last row predates the merge by ~27h, so the table was already
> quiet. **That is an over-read and is withdrawn.** The series is 60 rows over an 11-day

> (**2026-09-01**, **2026-09-04**) that predate all of this. A ~40h gap sits at the edge of

> separable from the row count. **The load-bearing evidence is the log data below** — zero
> `POST /api/v1/events` in 4,449 events — plus the fact that PR 28 touched only

**Consequence: the integration check the author explicitly asked for will never happen

### What I could retro-fit read-only

The author flagged "the jsonb round-trip against real Postgres" as not verified. I closed
most of that gap without writing:

- **The 6-column INSERT is sufficient.** `id` and `occurred_at` are the only other
  `NOT NULL` columns and both carry defaults (`nextval(...)`, `now()`). No omitted column
  can fail the insert.
- **`meta` is `jsonb`, nullable, no default** — so the `meta=None` default path is valid.
- **`CAST(:meta AS jsonb)` accepts exactly what `json.dumps(separators=(",",":"))` emits** —
  tested against the PR's stated `{"token_presented":true}` shape, a nested/unicode payload,
  `{}`, and `NULL`.
- **Negative control:** `CAST('{"broken":' AS jsonb)` raises `invalid input syntax for type
  json`. So the check above *could* have failed — it is not a green-by-construction test.

**Still unverified:** an actual `INSERT` round-trip. Read-only by mandate; I did not attempt
one even inside a transaction I would roll back.

### Two things confirmed as a side effect

- **`ALLOWED_EVENTS` and the DB CHECK constraint agree exactly.** App-side
  `{"impression","cta_click","dismiss"}` == `CHECK (event = ANY (ARRAY['impression',
  'cta_click','dismiss']))`. The code comment claims lockstep; measured against the live
  constraint, it holds. A mismatch here would be invisible in CI and would surface as a
  silently-swallowed 204.
- **`surface` has no DB allowlist** — only `CHECK (length(btrim(surface)) > 0)`. The app is
  stricter than the table, so `community_discord` needed no migration. This is the
  *inverse* of the PR's own "the table is not the contract" lesson, and worth recording in
  that direction too.

## Finding about the worklist generator itself

`verify-merges.py` classifies on the presence of a literal `VERIFY:` line. management-api#112
carries a genuinely falsifiable claim in prose and was still marked `UNFALSIFIABLE`. The
classifier's output is a *worklist*, not a verdict — an `UNFALSIFIABLE` row can still be
verifiable. Worth stating in the script's own output so a future reader does not treat the
label as the finding.
